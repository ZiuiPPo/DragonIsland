## 2. 最终可演示行为

### 2.1 仓库与拖拽

- 仓库用“原料 / 食物”按钮切页，各 20 格，共 40 格，每格上限为物品配置与 64 中的较小者。
- 种子、小麦、鸡蛋为原料；番茄、生菜、萝卜及料理成品为食物。
- 食物是否可吃由 `ItemData.can_eat()` 统一判断：`is_edible && !is_seed && satiety_restore > 0`。
- `is_ingredient` 与可直接食用相互独立：食物仍可以成为其他菜谱的材料。
- 左键拖整堆，Shift + 左键拖半堆（向上取整），右键拖一个。拖拽预览为物品图标和名称，不再显示数量。
- 同类合堆、空格拆堆，跨分类投放、不同物品合并、自身投放等情况被拒绝；整理只改格子布局，不改总库存。
- 拖拽到奶龙上每次消耗一份可吃食物；满饱腹时拒绝继续消耗，原料不能喂食。
- 喂食接收区域是 Control 的 UI 区域，四周扩大 12 像素，没有修改物理碰撞体。

### 2.2 奶龙的状态、音频与金币

- 当前饱腹值存于 `StaffMember.satiety`，范围 0–100。早期称“体力”，最终不维护另一套独立体力值。
- 未工作时沿用原有 NPC 随机漫游；实际移动速度超过阈值时才累加大笑触发计时。
- 累计移动随机 5–12 秒后，暂停漫游，进入大笑。
- 每次大笑随机持续 2–5 秒。每 0.10–0.18 秒随机切换大笑素材帧，避免所有奶龙动作一致。
- 大笑时播放 `assets/audio/nailong_laugh.mp3`；大笑结束、开始工作、饱腹耗尽或节点离开时停止播放。
- 仅实际大笑时，每秒消耗 2 点饱腹值、产生 50 金币。多只奶龙分别累计，收入叠加。
- 饱腹为 0 优先进入悲伤并停止移动，播放悲伤素材；喂食恢复后继续按当前工作标志活动。
- 工作时不触发闲置大笑，也不产生大笑收入。`StaffRegistry.set_working(id, bool)` 是接入接口，当前没有实现完整岗位派工系统。
- 头顶仅显示 `60/100` 一类数值，使用 14 号字，位置已调整至名字上方；去掉进度条、饥饿文字和悬停喂食提示。
- 员工状态面板底部“工作状态默认待定……”说明已删除。

### 2.3 料理台

侧栏只有“菜谱 / 料理台”一个烹饪入口。原建筑按钮已经恢复为主线原样的“建筑（尚未开放）”禁用占位，不连接料理台。菜谱按钮去掉图中的锁，并沿用其他已开放侧栏按钮的普通、悬停与按下样式。

打开后是模态大页面：左侧真实仓库（原料/食物可切换），中间工作台，右侧菜谱列表。Esc 或右上角关闭退出；农场时间不会暂停。

1. 选菜谱，显示所需材料、数量、产量与饱腹恢复值。
2. 从仓库拖到对应材料格，整堆拖入时自动截取所需数量；也可按“按菜谱备料”。
3. 投料是预览，不立即扣物品。右键撤回一个、清空投料、换菜谱、关窗均不损失物品。
4. 备料完整且仓库有空间后才能合成。合成时一次性验证、扣材料、加成品，然后发库存刷新事件。
5. 合成后切到食物页，成品自动入库；关窗后可以从侧栏仓库拖给奶龙吃。
6. 缺材料、满仓或重复点击不造成“扣了材料却没产出”或凭空复制物品。

## 5. 数据结构课设重点

### 5.1 字典：按 ID 找库存和物品

```gdscript
_items = {"wheat": 12, "egg": 6, "tomato": 8}
```

ID 是稳定英文字符串，显示中文名称由物品数据库提供。增减库存不用遍历所有格子找同名图片。字典查询/修改平均可视为 O(1)，这是使用引擎内置 Dictionary 的性质，本轮没有自行实现哈希表底层。

不要把“库存核心查询平均 O(1)”说成“整个 UI 刷新 O(1)”：事件发出后，界面还会进行遍历、排序与重绘。

### 5.2 数组：保存格子与名册

```gdscript
warehouse_slots = [
    {"item_id": "wheat", "amount": 8},
    {},
    {"item_id": "egg", "amount": 3}
]
```

数组下标对应格子，前 20 个为原料，后 20 个为食物。总库存字典回答“有多少”，格子数组回答“摆在哪”。拖拽整理仅修改摆放，生产、消费、合成才修改总量。

员工名册目前是 `Array[StaffMember]`；通过 ID 找员工仍是 O(N) 遍历，没有实现 ID 到员工的哈希索引。未来员工多时可以优化这一点。

### 5.3 配方与投料字典：无序、带数量的组合

```gdscript
recipe.ingredients = {"wheat": 2, "egg": 1}
staged = {"egg": 1, "wheat": 2}
```

投料先后顺序不同不会影响结果，比较的是物品 ID 和数量。不是把图片位置当作配方，也没有做“所有排列逐一枚举”的低效搜索。

当前是“用户先选菜谱，再按菜谱核对投料”，不是任意输入材料后自动推断菜谱。不能把未实现的自由配方搜索说成已有功能。

### 5.4 界面布局对账

仓库刷新先保留合法的已有格子，再按物品 ID 排序，将剩余库存按堆叠上限填入对应区域。旧的混排布局也借此迁移。设物品种类 M、格子数 S，主要开销约为 O(M log M + M×S + S)，本版 S 固定 40。

### 5.5 合成交易

`Inventory.can_exchange` 先复制库存进行试算：校验全部材料、试扣、试加输出，并计算两类仓库需要的格子数。单类需要格子数按各物品 `ceil(数量 / 堆叠上限)` 求和，不能超过 20。

全部通过后 `Inventory.exchange` 才更新真实库存，并发一次重载信号。过程没有 await，不会在“扣到一半”的位置把控制权交给另一个操作。这里是单线程游戏逻辑中的完整提交，不是数据库事务、并发锁或网络同步系统。

设库存种类 M、配方材料项 K、产物项 P，验证约 O(M+K+P)，提交的核心更新约 O(K+P)，不计事件触发后的 UI 对账。

## 6. 状态与经济结算的实现细节

行为优先级：饱腹耗尽 → 悲伤静止；否则工作 → 不触发闲置大笑；否则大笑计时中 → 大笑；否则 → 原有随机漫游。

这里使用状态标志和优先级条件实现行为切换，尚未改成完整的显式枚举岗位状态机。计时在物理帧中用 delta 推进，不在每帧重新抽一次“大笑是否发生”。音频只在进入大笑时启动，离开时停止，不会每帧从头播放。

有效结算时长：

```text
有效时长 = min(本次实际大笑时长, 剩余饱腹值 / 2)
饱腹消耗 = 有效时长 × 2
新增待结算收入 = 有效时长 × 50
```

例如剩 0.2 饱腹值却收到 1 秒的结算请求，只能再笑 0.1 秒，奖励 5 金币，而不是 50。两只奶龙各笑 1 秒，共 100 金币。

每累计一秒发 50 金币，停止大笑时补发不足一秒的整数金额，留下的小数存进 `laugh_gold_pending`，随员工保存。这样不因帧率不同、频繁停止或存读而反复丢掉小数尾数。

## 10. 常见答辩追问与参考回答

**为什么库存用字典，格子又用数组？**
字典适合按物品 ID 统计总量，数组适合按下标维护空间顺序。两者负责不同问题，避免整理格子时误改库存。

**如何保证拖拽不会复制物品？**
拖拽负载只是操作描述；落点先校验来源、物品 ID 和数量，再统一执行。仓库整理数量守恒；喂食真实扣库存；投料只是预览，合成才一次提交。

**如何避免合成扣了材料却没产物？**
先在副本试算所有成本和输出容量，全部满足才修改真实数据。失败不写入，提交时不做异步等待。

**合成为什么不要求投料顺序？**
配方是物品到数量的映射，比较数量关系而非数组排列顺序。

**帧率不同会导致赚的钱不同吗？**
按 delta 的有效大笑时长计算，不按“每帧加固定金币”。饱腹将耗尽时截断有效时长，小数收入继续累计。

**如何支持更多奶龙？**
每只奶龙拥有独立饱腹、计时和收入待结算数据，共享同一个金币入口。目前员工 ID 查询是线性的，更多员工时可增加字典索引，进一步合并 UI 刷新和音频表现。尚未做大规模性能压测，不能宣称支持无限员工。

**增加新菜需要改哪些地方？**
添加 ItemData 资源、图标和 RecipeData 资源，在 RecipeBook.IDS 注册。工作台、库存分类、喂食和存档能复用已有逻辑。

**你实现了 A*、队列或链表吗？**
本轮核心使用字典和数组。NPC 移动复用了原有 NpcLocomotion；没有为本轮手写 A*、队列或链表。课程若要求这些内容，需要后续按真实需求补充，而不能只改名字来声称已使用。

## 11. 当前限制及下一步

- 当前有可验证的合成、喂食、大笑收入链，但主线尚未接通所有材料的持续生产或购买；测试补给不等于完整生产经济系统。
- 仅有五道固定配方，没有解锁树、烹饪耗时、失败料理、自动烹饪或批量制作。
- 工作标志是接口，未完成岗位派工和路径工作逻辑。
- 仓库固定两类各 20 格；合成会阻止超容量。现有 Inventory.add 是基础入库接口，未来统一接入大量生产时，应在所有入库入口都补容量策略，而不是只依赖合成校验。
- 数值目前用于演示，不代表完成长期经济平衡。可以后续观察每种料理的材料成本、饱腹收益、笑声收入与招聘开销。
- 本次未完成组长审核或合并到 master，功能分支推送成功只表示远程可审阅。
